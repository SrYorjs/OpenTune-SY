# 3.2 — Estructura core/designsystem

Fecha: 2026-10-10  
Rama: `opentune-rebuild-v1`

## Resultado

Se creó la frontera estable:

```
core/designsystem/
├── DesignSystem.kt
├── theme/
│   └── DesignSystemTheme.kt
├── glass/
├── component/
└── preview/
```

Los directorios todavía no implementan los tokens de etapas posteriores. Esto es
intencional: 3.2 define propiedad y dependencias; 3.3–3.14 llenarán cada área.

## Integración

`OpenTuneTheme` continúa siendo el propietario del tema real:

```
OpenTuneTheme
    ↓
MaterialExpressiveTheme
    ↓
ProvideOpenTuneDesignSystem
    ↓
App UI
```

Por lo tanto esta etapa no cambia:

- ColorScheme;
- tipografía;
- pure black;
- dynamic theme;
- MotionScheme;
- Liquid Glass;
- tamaños;
- shapes;
- componentes existentes.

## Contrato de dependencias

`core/designsystem` puede depender de Compose/Material y de sus propios contratos,
pero no de estado o lógica de features.

Dependencias prohibidas desde Design System:

- ViewModels;
- Sources/proveedores;
- playback/service;
- Room/database;
- Innertube/network.

Los features sí podrán consumir Design System.

## Compatibilidad

Las implementaciones actuales permanecen en sus ubicaciones durante la migración:

- `ui/theme/Theme.kt`;
- `ui/theme/Type.kt`;
- `ui/component/LiquidGlassBackdrop.kt`;
- `ui/component/LiquidGlassControls.kt`;
- componentes legacy.

Esto evita un big-bang refactor. Cada bloque 3.x migrará una responsabilidad concreta.

## Protección

`DesignSystemArchitectureTest` comprueba:

1. que el package skeleton exista;
2. que OpenTuneTheme instale el provider;
3. que Design System no dependa de features;
4. que 3.2 no haya eliminado prematuramente la implementación visual existente.
