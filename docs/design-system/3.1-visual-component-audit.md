# 3.1 — Auditoría visual y de componentes actuales

Fecha de auditoría: 2026-10-10  
Rama: `opentune-rebuild-v1`

## Objetivo

Establecer el punto de partida del Design System antes de modificar la apariencia de OpenTune.

Esta fase **no cambia la UI**. Documenta qué ya está centralizado, qué sigue duplicado y qué debe convertirse en tokens/componentes compartidos durante 3.2–3.16.

---

## Resumen ejecutivo

OpenTune ya tiene una base visual moderna, pero todavía funciona como una colección de sistemas parciales en lugar de un único Design System.

### Fortalezas existentes

- `OpenTuneTheme` centraliza el esquema de color, modo oscuro, pure black y color dinámico.
- Se usa `MaterialExpressiveTheme`.
- Existe un `MotionScheme.expressive()` global.
- La tipografía completa de Material 3 ya está definida en `Type.kt`.
- Existe un motor central de Liquid Glass mediante `liquidGlassSurface()`.
- Existen controles compartidos de glass: icon button, pill button, cluster y card.
- Hay dimensiones estructurales compartidas para app bar, mini player, navegación, thumbnails y bottom sheet.
- La UI principal ya dispone de varios componentes reutilizables.
- La búsqueda nueva usa únicamente Universal y ya no necesita componentes visuales específicos por proveedor.

### Problemas principales

1. No existe todavía un paquete `core/designsystem` ni una API visual única.
2. No hay una escala global de spacing semántico.
3. No hay un sistema global de shapes; muchos radios están hardcodeados.
4. Hay transparencias y colores directos distribuidos por pantallas.
5. El motion global convive con muchos `spring()` y `tween()` locales.
6. Liquid Glass está centralizado a medias: existe un motor común, pero mantiene parámetros ópticos locales y compatibilidad legacy.
7. `Items.kt` y `PlayerComponents.kt` concentran demasiadas responsabilidades visuales.
8. Home, Search, Library, Player y Settings todavía usan diferentes convenciones de tamaño, radius y superficie.
9. Existen componentes especializados que deberían converger hacia primitivas compartidas.
10. El Player es el área con mayor deuda visual y debe migrarse después de estabilizar los tokens.

---

# 1. Tema y color

## Estado actual

Archivo principal:

`ui/theme/Theme.kt`

Actualmente ofrece:

- esquema dinámico del sistema;
- color personalizado;
- seed palette;
- light/dark;
- pure black;
- superficies premium;
- animación de transición de todo el `ColorScheme`;
- selección de tipografía;
- Material 3 Expressive.

Esto es una buena base y **no debe reemplazarse** durante 3.x.

## Problema

Las pantallas siguen usando decisiones locales como:

- `Color.Black`;
- `Color.White`;
- `Color.Transparent`;
- `color.copy(alpha = ...)`;
- overlays oscuros locales;
- borders con alpha propio.

Ejemplos con alta concentración de decisiones locales:

| Archivo | Observación |
| --- | --- |
| `Player.kt` | gran cantidad de overlays directos y alphas |
| `PlayerComponents.kt` | mayor concentración de color/alpha local |
| `HomeScreenComponents.kt` | tarjetas con tratamientos de color propios |
| `MainActivityChrome.kt` | chrome/navegación con reglas visuales específicas |
| `UniversalSearchScreen.kt` | badges y superficies definidos localmente |

## Decisión para Design System

Mantener `ColorScheme` como fuente base y añadir roles semánticos propios, por ejemplo:

- `surfaceGlass`
- `surfaceGlassStrong`
- `surfaceInteractive`
- `surfacePlayer`
- `outlineGlass`
- `overlayScrim`
- `overlayArtwork`
- `accentPositive`
- `accentWarning`
- `textMuted`

No introducir colores de marca/provider como colores globales de UI salvo donde tengan significado real.

# 2. Tipografía

## Estado actual

`ui/theme/Type.kt` ya define toda la jerarquía Material:

- displayLarge / Medium / Small
- headlineLarge / Medium / Small
- titleLarge / Medium / Small
- bodyLarge / Medium / Small
- labelLarge / Medium / Small

También soporta:

- OpenTune font;
- system font;
- Monocraft.

## Evaluación

**Estado: bueno.**

No hace falta reconstruir tipografía desde cero.

## Mejora necesaria

Crear aliases semánticos para evitar que cada pantalla decida por sí sola si algo debe ser `titleSmall`, `bodyMedium`, etc.

Ejemplos futuros:

- `screenTitle`
- `sectionTitle`
- `songTitle`
- `songSubtitle`
- `metadata`
- `badge`
- `playerTitle`

La implementación debe seguir derivando de `MaterialTheme.typography`.

# 3. Spacing y dimensiones

## Base existente

`constants/Dimensions.kt` ya centraliza dimensiones estructurales como:

- FloatingToolbarHeight = 72.dp
- SlimFloatingToolbarHeight = 64.dp
- MiniPlayerHeight = 64.dp
- AppBarHeight = 64.dp
- ListItemHeight = 72.dp
- SuggestionItemHeight = 60.dp
- ListThumbnailSize = 54.dp
- GridThumbnailHeight = 148.dp
- AlbumThumbnailSize = 156.dp
- PlayerHorizontalPadding = 32.dp

## Problema

Estas son dimensiones de componentes, **no un spacing system**.

Hay muchos valores directos como:

`4.dp, 6.dp, 8.dp, 10.dp, 12.dp, 14.dp, 16.dp, 18.dp, 20.dp, 22.dp, 24.dp, 26.dp, 28.dp, 30.dp, 32.dp...`

Esto permite pequeñas diferencias visuales entre superficies equivalentes.

Ejemplos:

- `Items.kt`: decenas de valores dp distintos.
- `PlayerComponents.kt`: cientos de usos de dp locales.
- `UniversalSearchScreen.kt`: spacing y tamaños de badges definidos in situ.
- `HomeScreenComponents.kt`: cards y paddings propios.

## Decisión para Design System

Crear una escala semántica compacta:

```
spacing.xs
spacing.sm
spacing.md
spacing.lg
spacing.xl
spacing.xxl
```

y tamaños funcionales separados:

```
touchTarget
iconSmall
iconMedium
iconLarge
artworkSmall
artworkMedium
artworkLarge
```

No reemplazar automáticamente todo número dp: solo valores que representan decisiones visuales compartidas.

# 4. Shapes

## Base existente

Actualmente existen algunos valores centralizados:

- `ThumbnailCornerRadius = 14.dp`
- `GridThumbnailCornerRadius = 18.dp`

Liquid Glass también usa shapes propias.

## Problema

No se pasa un sistema `Shapes` al tema.

Los componentes definen localmente radios como:

- 8.dp
- 10.dp
- 12.dp
- 14.dp
- 16.dp
- 17.dp
- 18.dp
- 20.dp
- 22.dp
- 24.dp
- 26.dp
- 28.dp
- 30.dp
- 32.dp
- 50%

Esto hace que dos cards equivalentes tengan identidad ligeramente distinta.

## Caso crítico

`PlayerComponents.kt` contiene muchas shapes distintas dentro del mismo subsistema.

## Decisión

Crear roles:

- `extraSmall`
- `small`
- `medium`
- `large`
- `extraLarge`
- `pill`
- `artwork`
- `playerArtwork`
- `sheet`

La preferencia de corner radius del usuario seguirá siendo respetada para artwork.

# 5. Liquid Glass

## Base existente

Archivos principales:

- `LiquidGlassBackdrop.kt`
- `LiquidGlassControls.kt`

Existe:

- `LocalEnableLiquidGlass`;
- `LocalLiquidBackdrop`;
- `LocalSky`;
- `liquidGlassSurface()`;
- blur;
- lens;
- vibrancy;
- refraction;
- dispersion;
- highlight;
- inner shadow;
- fallback para dispositivos sin backdrop.

Además existen:

- `LiquidGlassIconButton`
- `LiquidGlassPillButton`
- `LiquidGlassControlCluster`
- `LiquidGlassCard`

## Evaluación

La arquitectura base es buena.

## Problema

Los parámetros ópticos todavía están codificados por control:

- blurRadius;
- refraction;
- curve;
- dispersion;
- edge;
- highlight alpha;
- border alpha;
- fallback alpha.

Además `LocalSky` permanece para pantallas legacy.

## Decisión

Liquid Glass debe convertirse en un **material del Design System**, no una colección de efectos.

Futuros presets:

- `GlassStyle.Navigation`
- `GlassStyle.Control`
- `GlassStyle.Card`
- `GlassStyle.Sheet`
- `GlassStyle.Player`
- `GlassStyle.Subtle`

Cada preset define óptica, border, tint y motion.

No eliminar `LocalSky` hasta terminar la migración visual y confirmar que ninguna pantalla lo necesita.

# 6. Motion

## Base existente

`OpenTuneTheme` utiliza:

`MotionScheme.expressive()`

Además existen algunas specs compartidas:

- `NavigationBarAnimationSpec`
- `BottomSheetAnimationSpec`
- `BottomSheetSoftAnimationSpec`

## Problema

Muchos componentes siguen declarando:

- `spring()` local;
- stiffness local;
- damping ratio local;
- `tween()` local;
- duraciones locales.

Caso más visible:

`PlayerComponents.kt` contiene una gran cantidad de springs y tweens independientes.

## Decisión

3.8 deberá introducir motion tokens por intención:

- `press`
- `selection`
- `enter`
- `exit`
- `expand`
- `collapse`
- `sharedElement`
- `playerControl`
- `glassElastic`

No uniformar todos los movimientos con una sola duración.

# 7. Sistema de items

## Archivo crítico

`ui/component/Items.kt`

Tamaño auditado: aproximadamente **2257 líneas**.

Contiene alrededor de **75 composables** y múltiples familias:

- ListItem
- GridItem
- SongListItem
- SongGridItem
- ArtistListItem
- ArtistGridItem
- AlbumListItem
- AlbumGridItem
- PlaylistListItem
- PlaylistGridItem
- MediaMetadataListItem
- YouTubeListItem
- YouTubeGridItem
- Local grids
- thumbnails
- swipe behaviors
- library feature cards

## Problema

El archivo mezcla:

1. layout;
2. styling;
3. artwork;
4. provider-specific UI;
5. gestures;
6. badges;
7. library cards.

## Decisión

Durante 3.10 debe dividirse conceptualmente en:

```
designsystem/component/
  Artwork.kt
  MediaListItem.kt
  SongRow.kt
  AlbumCard.kt
  ArtistCard.kt
  PlaylistCard.kt
  MediaBadge.kt
```

Las pantallas no deberían tener que saber cómo construir manualmente el mismo media item.

# 8. Player UI

## Archivos principales

- `Player.kt`
- `PlayerComponents.kt`
- `MiniPlayer.kt`
- `MiniPlayerComponents.kt`
- `Thumbnail.kt`
- `Queue.kt`
- `QueueComponents.kt`

## Hallazgo principal

`PlayerComponents.kt` es actualmente el mayor foco de deuda visual.

Auditoría aproximada:

- ~3418 líneas;
- ~15 bloques composable principales;
- más de 200 usos de dimensiones dp;
- decenas de shapes;
- gran cantidad de alphas locales;
- múltiples springs;
- múltiples tweens;
- varias reglas Liquid Glass;
- numerosos colores directos.

`Player.kt` también conserva numerosos overlays y decisiones locales.

## Decisión

No rehacer Player durante 3.1–3.9.

Primero se crean tokens/materiales/componentes base.  
Luego 3.10–3.16 migran primitivas compatibles.

La reconstrucción estructural grande sigue perteneciendo a **4 — Player 2.0**.

# 9. Home

## Estado

`HomeScreen.kt` está relativamente limpio.

La mayor parte de la UI está en:

`HomeScreenComponents.kt`

aprox. 1385 líneas.

## Problemas observados

- cards específicas con radios propios;
- alphas propios;
- overlays propios;
- motion propio;
- tamaños fijos;
- algunas cards replican patrones ya existentes en `Items.kt`.

## Decisión

Home debe ser de las primeras pantallas grandes en migrar al nuevo Design System porque tiene variedad visual suficiente para validar:

- cards;
- artwork;
- section headers;
- horizontal lists;
- pressed states;
- badges;
- glass.

# 10. Search

## Estado

La limpieza de Sources dejó Search en una situación favorable:

```
UniversalSearchScreen.kt
UniversalVersionQualityDialog.kt
```

Ya no existen pantallas visuales separadas por proveedor en la rama actual.

## Problemas visuales

`UniversalSearchScreen.kt` todavía contiene:

- radios directos;
- tamaños de iconos locales;
- badge styling local;
- spacing local;
- proveedor/calidad como UI específica de pantalla.

## Decisión

Search será una buena pantalla piloto después de Home para:

- `SongRow`;
- `ProviderBadge`;
- `QualityBadge`;
- `FilterChip`;
- estados loading/error;
- selector version/quality.

# 11. Library

## Estado

Library ya está dividida por dominio:

- LibraryScreen
- LibrarySongsScreen
- LibraryAlbumsScreen
- LibraryArtistsScreen
- LibraryPlaylistsScreen
- etc.

## Evaluación

La estructura funcional es razonable.

## Problema

Todavía consume familias de componentes visuales heredadas de `Items.kt` y convenciones propias de cada pantalla.

## Decisión

Migrar Library después de consolidar:

- SongRow;
- AlbumCard;
- ArtistCard;
- PlaylistCard;
- EmptyState;
- SortHeader.

No reconstruir su arquitectura de datos en Design System.

# 12. Settings

## Fortaleza

Settings ya tiene:

`SettingsDimensions.kt`

con dimensiones específicas del subsistema.

Esto demuestra que centralizar decisiones visuales ya funciona en el proyecto.

## Problema

Es un sistema paralelo, no parte de una escala global.

## Decisión

No borrar `SettingsDimensions` inmediatamente.

Primero crear tokens globales; después mapear Settings sobre ellos cuando exista equivalencia clara.

# 14. Duplicación / hotspots prioritarios

## Prioridad P0

### PlayerComponents.kt
Mayor dispersión de tamaños, shapes, motion, colors y glass.

### Items.kt
Demasiadas familias de media items en un único archivo.

### Liquid Glass parameters
Existe primitive central, pero no presets/tokens ópticos.

## Prioridad P1

### HomeScreenComponents.kt
Buen candidato para validar cards y motion tokens.

### UniversalSearchScreen.kt
Buen candidato para validar SongRow, badges y estados.

### MainActivityChrome / FloatingNavigationToolbar
Necesitan un único contrato de navigation surfaces.

## Prioridad P2

### Library
Principalmente migración de componentes compartidos.

### Settings
Ya tiene cierto orden interno; puede migrarse después.

# 15. Riesgos que debemos evitar

1. Rehacer Player antes de estabilizar tokens.
2. Cambiar todos los dp mediante búsqueda/reemplazo.
3. Convertir Liquid Glass en un modifier aplicado a todo.
4. Eliminar fallbacks de glass para hardware incompatible.
5. Romper preferencias actuales de pure black, dynamic theme o artwork radius.
6. Mezclar Design System con lógica de Sources.
7. Cambiar comportamiento funcional durante una migración visual.
8. Crear componentes tan genéricos que terminen con decenas de parámetros.
9. Duplicar MaterialTheme en lugar de extenderlo.
10. Introducir provider colors como base del tema.

# 17. Criterio de migración

Cada componente migrado debe cumplir:

- no contiene lógica de proveedor;
- no conoce ViewModels;
- usa roles/tokens en vez de números arbitrarios cuando aplica;
- respeta MaterialTheme;
- soporta dark/pure black;
- soporta Liquid Glass habilitado y deshabilitado;
- mantiene accesibilidad/touch target;
- evita asignaciones;
- conserva comportamiento actual;
- incluye previews o pruebas cuando tengan valor.

# Conclusión

OpenTune **no necesita otro tema nuevo**. Necesita convertir las buenas piezas que ya tiene en un sistema coherente.

La base más valiosa ya existe:

- Material 3 Expressive;
- dynamic colors;
- custom typography;
- Liquid Glass;
- reusable media UI;
- shared navigation/player infrastructure.

El trabajo de 3.x será reducir decisiones locales y convertirlas en contratos visuales compartidos.

El mayor beneficio esperado no es solo que la app se vea más uniforme: también será mucho más sencillo rehacer Player 2.0 sin volver a duplicar styling en cada layout.
