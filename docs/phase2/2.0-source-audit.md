# Phase 2.0 — Source audit

Branch audited: `opentune-rebuild-v1`

Baseline at the start of Phase 2: `50ab4f97b08b219a77a7b8e276004a52c2f30a0d`

## Scope

This checkpoint documents how music/catalog, playback, downloads, lyrics and animated artwork are wired today. It intentionally does **not** change runtime behavior.

OpenTune remains a YouTube Music client at this point. Phase 2 will add provider-neutral models and contracts incrementally; it must not remove existing YouTube Music capabilities.

## Current source map

| Area | Current implementation | Search/catalog | Audio playback today | Download/offline today | Phase 2 observation |
| --- | --- | --- | --- | --- | --- |
| YouTube Music / Innertube | `innertube` module, `YouTube`, `OnlineSearchViewModel`, playback utilities | Primary online search, browse and continuation paths | Native OpenTune playback path; stream data is resolved through the existing YouTube/Innertube playback stack | Media3 `DownloadManager` + OpenTune download cache; format metadata is persisted | This is the reference source and must be migrated first without behavior loss |
| Spotify | `spotify` module, account/library repository, playlist UI, `SpotifyPlaybackResolver` | Spotify catalog/account/library data exists | `SpotifyPlaybackResolver` searches YouTube Music, scores candidates and returns a YouTube-backed `MediaItem`; `spotifyTrackId` is retained as metadata | No independent Spotify audio download path was found in the current integration | Spotify is currently a catalog/library source plus a YouTube playback resolver, not an independent audio source |
| Deezer | `Deezer.kt`, `DeezerSearchViewModel`, `DeezerSearchScreen` | Read-only track search, trending, track details and metadata/audio-feature lookup | Deezer results are converted to `CatalogTrackReference`; `CatalogPlaybackResolver` searches YouTube Music and plays the matched YouTube result | No independent Deezer audio download path; a resolved YouTube item can use the normal OpenTune path | Deezer is currently isolated behind a separate search surface and behaves as catalog/discovery metadata |
| Local OpenTune library | Room entities/DAOs and `LocalSearchViewModel` | Searches locally stored songs, albums, artists and playlists | Uses existing stored media IDs and the normal player path | Downloaded YouTube media and local metadata live in the local database/cache | This is a local-library surface, not yet a provider-neutral `LocalMusicSource` contract |

## Direct coupling confirmed in the current code

- `OnlineSearchViewModel` calls `YouTube.searchSummary`, `YouTube.search` and `YouTube.searchContinuation` directly.
- `SpotifyPlaybackResolver` calls `YouTube.search` directly and uses `SpotifyMapper` to score the best YouTube Music match.
- `CatalogPlaybackResolver` calls `YouTube.search` directly for metadata-only catalog tracks.
- `DeezerSearchViewModel` calls the singleton `Deezer` client directly.
- `LocalSearchViewModel` calls `MusicDatabase` search flows directly.
- `DownloadUtil` is YouTube-specific for stream resolution and persists YouTube format information.
- Lyrics and animated artwork already have their own provider-style abstractions, but they are not part of a unified music-source model.

These are the seams that later Phase 2 points will migrate. This checkpoint does not move them.

## Existing offline behavior that must not regress

The current download stack already does more than audio:

1. Media3 downloads the playable audio into the download cache.
2. The chosen YouTube format is persisted, including MIME/codec, bitrate and sample rate when available.
3. Lyrics are fetched and stored locally.
4. Static cover artwork is cached.
5. Animated artwork/Canvas is cached when available, including local rewriting of HLS playlists and segments.

Phase 2 must preserve this behavior while making it source-aware. A future offline model should record the exact downloaded source/variant and quality rather than replacing the existing Media3 pipeline prematurely.

## Architecture constraints for Phase 2

- YouTube Music remains the primary known-good source during migration.
- A conceptual track must be separable from a provider-specific result.
- One conceptual track may have several provider variants.
- Provider IDs must not be reused as the universal identity.
- Matching must preserve versions such as original, remaster, live, remix, acoustic, cover, sped-up/slowed and music video.
- Audio quality belongs to a source variant/offline edition, not to the conceptual track itself.
- Search, Home, Library and Player are **not** migrated in points 2.0 or 2.1.
- `MusicSource`, `SourceCapabilities`, `SourceRegistry`, `SourceResolver` and `TrackMatcher` are deliberately deferred to later Phase 2 checkpoints.

## Point 2.0 result

The present codebase is multi-catalog but not yet multi-audio-provider:

- YouTube Music is the actual primary playback/download engine.
- Spotify and Deezer currently resolve playback through YouTube Music.
- Lyrics and Canvas already aggregate multiple providers independently.
- Offline audio/assets already have a useful foundation that Phase 2 should wrap and generalize rather than discard.
